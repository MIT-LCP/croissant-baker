Real htslib-written genomic fixtures
====================================

Written by pysam 0.24.1, which bundles htslib and samtools 1.24. Every file in
this directory is an encoder's own output: the containers, their headers and
their index files were produced by htslib, not by a test helper spelling the
specification out a second time.

Synthetic. No human data, no consented sample, no real cohort. The two contigs
(chr1, 400 bases; chr2, 300 bases) are pseudo-random sequence generated by a
fixed linear congruential recurrence seeded from the contig name, so the same
bases come out on every run, and the five 50-base reads are substrings of them.
The identifiers NA00001 and NA00002 are the placeholder sample names the VCF
specification itself uses in its examples.

Recipe. A generator script built the SAM header in memory (@HD VN:1.6
SO:coordinate; @SQ chr1 with AS:GRCh38 and @SQ chr2; one @RG with PL:ILLUMINA,
CN:STJUDE, SM:NA00001; an @PG chain of bwa 0.7.17 then samtools 1.19), wrote
the five reads through pysam.AlignmentFile as SAM, as BAM, and as CRAM at
format versions 2.1, 3.0 and 3.1, indexed the BAM and the two CRAMs that accept
an index, and emitted the reads again as FASTQ and the two contigs as an
faidx-indexed FASTA. It then wrote a VCFv4.3 text callset (contigs chr1 and
chr2; INFO keys NS, AF, DB and ANN; FORMAT keys GT, DP and GQ; samples NA00001
and NA00002), converted it to BCF through pysam.VariantFile and indexed that.
The script is not committed: the files are the fixture, and regenerating them
with a different htslib would defeat the point of tracking an encoder's output.

v10.cram is the one exception. It is a CRAM 1.0 file definition that htslib
wrote before refusing to continue, kept because a version the handler declines
to walk is worth having a real example of.
