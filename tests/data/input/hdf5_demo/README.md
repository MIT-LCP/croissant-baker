# HDF5 demo (single-cell + one file from outside single-cell)

A small fixture used by `tests/test_end_to_end.py`. The layout mirrors the
shape a GEO series arrives in, so one bake exercises both of the HDF5
handler's views at once.

```
hdf5_demo/
├── GSM000001/filtered_feature_bc_matrix.h5   10x feature-barcode matrix, 40 features x 300 barcodes
├── GSM000002/filtered_feature_bc_matrix.h5   the same, under a second sample directory
├── integrated.h5ad                           AnnData, 120 observations x 20 variables
├── environment.hdf5                           NetCDF4-shaped: matches no layout
└── README.md                                  this file, which no handler claims
```

Two samples sharing one basename is what forces the identifier
disambiguation: a bare basename would give both
`filtered_feature_bc_matrix.h5` files the same record set.

## Source

**Synthetic.** These files were not downloaded; they were written by
`tests/hdf5_fixtures.py` from the two formats' published on-disk
specifications, and committed so the integration test reads frozen bytes
rather than whatever the builders happen to produce today.

No real vendor output was available to trim and redistribute, so what this
fixture cannot show is that a Cell Ranger or `anndata` file opens. Each layout
was instead checked against the real reader while it was written:

- `integrated.h5ad` is read by `anndata` 0.13.3 with all eight `obs` columns
  at their intended dtypes (`str`, two `category`, `int64`, `float32`, `bool`,
  `Int64`, `boolean`).
- both `filtered_feature_bc_matrix.h5` files are read by
  `scanpy.read_10x_h5` as 300 observations of 40 variables, which is what
  confirms `shape = [n_features, n_barcodes]`.

Neither `anndata` nor `scanpy` is a dependency of this package, so those
checks are recorded here rather than run in CI.

If a small real HDF5 file turns up in a PhysioNet dataset, adding it as a
second end-to-end case would be worth more than this one.

## Regenerating

```python
from pathlib import Path
from tests import hdf5_fixtures as fx

demo = Path("tests/data/input/hdf5_demo")
for sample in ("GSM000001", "GSM000002"):
    fx.write_tenx(demo / sample / "filtered_feature_bc_matrix.h5", 40, 300)
fx.write_h5ad(demo / "integrated.h5ad", n_obs=120, n_var=20)
fx.write_netcdf(demo / "environment.hdf5")
```

The output is byte-identical between runs, so regenerating an unchanged
fixture leaves the working tree clean.

## The golden

`tests/data/output/hdf5_demo_croissant.jsonld` is the document this dataset
bakes to, and `test_hdf5_demo_generation` reads it rather than overwriting it —
the only end-to-end case that does. A deliberate change to what the HDF5
handler emits therefore shows up as a diff in that file, and is regenerated by
pointing the CLI at this directory with the same flags the test uses:

```
croissant-baker -i tests/data/input/hdf5_demo \
  -o tests/data/output/hdf5_demo_croissant.jsonld \
  --name "HDF5 demo (synthetic single-cell series)" \
  --description "Two 10x feature matrices, an integrated AnnData object, and a NetCDF4 file" \
  --url https://example.org/hdf5-demo \
  --license https://creativecommons.org/licenses/by/4.0/ \
  --dataset-version 1.0.0 --date-published 2026-01-01 \
  --creator "croissant-baker test suite"
```
